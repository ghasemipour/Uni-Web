# پاسخ تمرین Git

## سؤال ۱: تفاوت `git merge` و `git rebase`

هر دو دستور برای ترکیب تغییرات برنچ ها استفاده می‌شوند، اما تاریخچه را متفاوت می‌کنند.

- `git merge` تغییرات برنچ دیگر را با برنچ فعلی ترکیب می‌کند. اگر برنج ها از هم جدا شده باشند، معمولاً یک **merge commit** ساخته می‌شود و تاریخچهٔ هر دو برنچ حفظ می‌شود.
- `git rebase` کامیت‌های برنچ فعلی را روی نوک برنچ مقصد دوباره اعمال می‌کند. در نتیجه تاریخچه معمولاً خطی‌تر می‌شود، اما شناسهٔ کامیت‌های بازاعمال‌شده تغییر می‌کند.

**مثال برای `merge`:** وقتی چند نفر روی برنج های جداگانه کار کرده‌اند و می‌خواهیم تغییرات را بدون بازنویسی تاریخچهٔ موجود ترکیب کنیم:

```bash
git switch main
git merge feature-login
```

این روش برای برنج های مشترک مناسب است؛ چون تاریخچهٔ قبلی کامیت‌ها را حفظ می‌کند.

**مثال  برای `rebase`:** وقتی روی یک برنچ شخصی کار می‌کنیم و می‌خواهیم تغییرات جدید `main` را پیش از ادغام دریافت کنیم:

```bash
git switch feature-login
git fetch origin
git rebase origin/main
```

این کار تاریخچه را مرتب و خطی می‌کند. بهتر است شاخه‌ای را که دیگران هم از آن استفاده می‌کنند بدون هماهنگی `rebase` نکنیم، چون تاریخچهٔ آن بازنویسی می‌شود.

## سؤال ۲: انتخاب بخشی از تغییرات با `hunk`

در خروجی `git diff`، هر **hunk** بخشی از فایل است که خطوط تغییرکرده و چند خط اطراف آن را نشان می‌دهد. با انتخاب تعاملی می‌توان فقط بخش‌های موردنظر را وارد ناحیهٔ `staging` کرد.

```bash
git add -p README.md
```

Git هر بخش را نمایش می‌دهد و گزینه‌هایی ارائه می‌کند؛ مهم‌ترین آن‌ها:

- `y`: افزودن این بخش به `staging`
- `n`: رد کردن این بخش
- `s`: تقسیم بخش به بخش‌های کوچک‌تر، در صورت امکان
- `e`: ویرایش دستی بخش
- `q`: خروج از حالت تعاملی

پس از انتخاب بخش‌ها، وضعیت و تفاوت‌های آمادهٔ کامیت را بررسی می‌کنیم:

```bash
git diff
git diff --cached
git status
```

`git diff` تغییرات unstaged را نشان می‌دهد و `git diff --cached` تغییرات staged را نمایش می‌دهد. این روش کمک می‌کند هر کامیت هدف مشخص و تغییرات مرتبط داشته باشد و تغییرات نامرتبط با هم ثبت نشوند.

## سؤال ۳: یافتن منشأ خطا با `git bisect`

دستور `git bisect` با جست‌وجوی دودویی، کامیتی را پیدا می‌کند که بین یک نسخهٔ سالم و یک نسخهٔ خراب، خطا را وارد کرده است.

ابتدا یک کامیت خراب و یک کامیت سالم مشخص می‌کنیم:

```bash
git bisect start
git bisect bad
git bisect good <good-commit>
```

Git یک کامیت میانی را checkout می‌کند. آن نسخه را آزمایش می‌کنیم و نتیجه را اعلام می‌کنیم:

```bash
git bisect good
# یا اگر خطا وجود دارد:
git bisect bad
```

این کار تا مشخص شدن کامیت مشکل‌ساز ادامه پیدا می‌کند. در پایان جست‌وجو را خاتمه می‌دهیم:

```bash
git bisect reset
```

**مثال:** فرض کنید برنامه در نسخهٔ فعلی هنگام ورود کاربر خطا می‌دهد، اما در کامیت قدیمی‌تر درست کار می‌کرده است. با اجرای آزمون ورود روی نسخه‌های میانی و اعلام `good` یا `bad`، Git محدوده را هر بار نصف می‌کند و سریع‌تر از بررسی تک‌تک کامیت‌ها به منشأ خطا می‌رسد.

## سؤال ۴: بررسی تغییرات پیش از کامیت

### ۱. بررسی وضعیت و تفاوت‌ها

```bash
git status
git diff
git diff --cached
```

- `git status` وضعیت فایل‌های staged، unstaged و untracked را نشان می‌دهد.
- `git diff` تغییرات انجام‌شده‌ای را نشان می‌دهد که هنوز وارد staging نشده‌اند.
- `git diff --cached` تغییراتی را نشان می‌دهد که در staging هستند و برای کامیت بعدی آماده‌اند.

در سناریوی سؤال، بخشی از تغییرات `README.md` وارد staging شده و سپس فایل دوباره ویرایش شده است؛ بنابراین ممکن است هم تغییر staged و هم تغییر unstaged برای یک فایل وجود داشته باشد.

### ۲. اگر بدون `-a` کامیت کنیم چه می‌شود؟

```bash
git commit -m "Update README"
```

فقط تغییراتی ثبت می‌شوند که از قبل در staging قرار دارند. تغییرات جدیدی که پس از `git add` ایجاد شده‌اند، unstaged باقی می‌مانند. گزینهٔ `-a` نیز فایل‌های untracked را اضافه نمی‌کند و برای این سناریو لازم نیست.

### ۳. نادیده گرفتن پوشهٔ `tmp/`

در فایل `.gitignore` در ریشهٔ مخزن این خط را اضافه می‌کنیم:

```gitignore
tmp/
```

این قاعده فایل‌های untracked داخل پوشهٔ `tmp/` را از پیگیری Git مستثنا می‌کند. اما `.gitignore` به‌تنهایی فایل‌هایی را که قبلاً tracked شده‌اند از پیگیری خارج نمی‌کند. برای خارج کردن فایل‌های tracked از شاخص Git، بدون حذف فایل‌های محلی، می‌توان از این دستور استفاده کرد:

```bash
git rm -r --cached tmp/
```

سپس تغییر `.gitignore` و حذف از شاخص را کامیت می‌کنیم. در سناریوی سؤال، چون فایل‌های `tmp/` untracked هستند، افزودن قاعده به `.gitignore` کافی است.

## سؤال ۵: رفع `merge conflict` در کار گروهی

### ۱. چرا conflict رخ می‌دهد؟

در این سناریو، هر دو شاخه یک خط از `README.md` را به متن‌های متفاوت تغییر داده‌اند. Git نمی‌تواند به‌طور خودکار تشخیص دهد کدام متن باید باقی بماند؛ بنابراین `merge conflict` ایجاد می‌شود.

تغییر هر دو نفر در یک فایل الزاماً conflict ایجاد نمی‌کند. اگر تغییرها در بخش‌های جداگانه باشند یا Git بتواند آن‌ها را خودکار ترکیب کند، ممکن است merge بدون conflict انجام شود.

### ۲. شناسایی فایل و نسخه‌های متعارض

```bash
git status
```

این دستور فایل‌های دارای conflict را نشان می‌دهد. درون فایل، conflict markers معمولاً به این شکل هستند:

```text
<<<<<<< HEAD
متن برنچ فعلی
=======
متن برنچ دیگر
>>>>>>> feature-description
```

بخش بالایی تغییر برنچ فعلی و بخش پایینی تغییر برنچ ادغام‌شونده را نشان می‌دهد. نام و جزئیات دقیق markerها ممکن است با وضعیت merge فرق کند.

### ۳. حفظ اطلاعات هر دو تغییر و تکمیل merge

فایل را باز می‌کنیم و متن نهایی‌ای می‌نویسیم که اطلاعات لازم از هر دو تغییر را حفظ کند. سپس همهٔ markerها را حذف و نتیجه را بررسی می‌کنیم.

```bash
git diff
git status
```

پس از حل conflict، فایل را stage و merge را تکمیل می‌کنیم:

```bash
git add README.md
git diff --cached
git commit
```

اگر Git هنگام merge یک پیام کامیت آماده کرده باشد، معمولاً می‌توان همان پیام را در ویرایشگر تأیید کرد. برای اطمینان از باقی نماندن markerها، متن نهایی فایل را بررسی می‌کنیم و در صورت نیاز جست‌وجو انجام می‌دهیم:

```bash
git diff --check
git grep -n -E '^(<<<<<<<|=======|>>>>>>>)' -- README.md
```

دستور `git diff --check` مشکلاتی مانند whitespace نامناسب را بررسی می‌کند؛ جست‌وجوی دوم نیز markerهای معمول را در فایل پیدا می‌کند. اگر خروجی جست‌وجو نشان دهد marker باقی مانده، باید آن را اصلاح کنیم.

### ۴. لغو merge در حال انجام

اگر تصمیم بگیریم merge را ادامه ندهیم و عملیات هنوز در جریان باشد:

```bash
git merge --abort
```

این دستور تلاش می‌کند وضعیت شاخه را به قبل از شروع merge برگرداند. بهتر است پیش از شروع merge، working tree تمیز باشد تا بازگردانی مطمئن‌تر انجام شود.

## سؤال ۶: انتخاب روش مناسب برای بازگرداندن تغییرات

### ۱. دور انداختن تغییر unstaged در `notes.txt`

چون تغییر فایل وارد staging نشده و می‌خواهیم فقط تغییرات همین فایل کنار گذاشته شوند، از دستور زیر استفاده می‌کنیم:

```bash
git restore -- notes.txt
```

این دستور تغییرات unstaged فایل را با نسخهٔ موجود در staging جایگزین می‌کند. طبق صورت سؤال، نسخهٔ staging با آخرین کامیت یکسان است؛ پس فایل به محتوای آخرین کامیت برمی‌گردد و فایل‌های دیگر تغییر نمی‌کنند. این عملیات تغییرات فایل را از بین می‌برد، بنابراین باید مطمئن باشیم به آن‌ها نیاز نداریم.

### ۲. خارج کردن `notes.txt` از staging و حفظ ویرایش‌ها

برای خارج کردن فایل از staging بدون حذف تغییرات working tree:

```bash
git restore --staged -- notes.txt
```

این دستور نسخهٔ staging را با نسخهٔ `HEAD` هماهنگ می‌کند، اما ویرایش‌های فایل در working tree را حفظ می‌کند. بنابراین تغییرات همچنان وجود دارند، ولی برای کامیت بعدی آماده نیستند.

### ۳. برگرداندن اثر کامیت اشتباه روی `main` مشترک

چون کامیت اشتباه به برنچ مشترک `main` push شده و هم‌تیمی‌ها آن را دریافت کرده‌اند، روش امن‌تر استفاده از `git revert` است:

```bash
git revert <commit-id>
git push origin main
```

`git revert` یک کامیت جدید می‌سازد که تغییرات کامیت مشخص‌شده را معکوس می‌کند؛ در نتیجه تاریخچهٔ موجود حذف یا بازنویسی نمی‌شود. این روش برای برنچ مشترک مناسب‌تر است، چون کامیت‌های دریافت‌شده توسط هم‌تیمی‌ها همچنان در تاریخچه باقی می‌مانند.

در مقابل، حذف کامیت از تاریخچه با reset و سپس `force push` می‌تواند تاریخچهٔ برنچ مشترک را بازنویسی کند و کار دیگران را مختل سازد؛ بنابراین در این سناریو انتخاب مناسبی نیست.

## سؤال یک: تفاوت نسخه‌های HTTP

<div dir="rtl">

### تفاوت نسخه‌ها

**۱. HTTP/0.9**

نسخه‌ای بسیار ساده از HTTP بود که فقط از متد `GET` پشتیبانی می‌کرد. در این نسخه هدرهای درخواست و پاسخ و کدهای وضعیت وجود نداشتند و پاسخ معمولاً فقط شامل محتوای سند HTML بود.

**۲. HTTP/1.0**

در این نسخه هدرهای درخواست و پاسخ، کدهای وضعیت و پشتیبانی از انواع مختلف محتوا اضافه شدند. معمولاً برای هر درخواست یک اتصال TCP جداگانه ایجاد می‌شد.

**۳. HTTP/1.1**

این نسخه اتصال پایدار (`Persistent Connection`) را معرفی کرد که امکان استفادهٔ مجدد از یک اتصال TCP برای چند درخواست را فراهم می‌کند. همچنین قابلیت‌هایی مانند هدر `Host`، درخواست‌های شرطی و انتقال قطعه‌ای داده‌ها را پشتیبانی می‌کند.

**۴. HTTP/2**

در این نسخه، پیام‌ها به فریم‌های دودویی تبدیل شدند و قابلیت `Multiplexing` امکان ارسال چند جریان درخواست و پاسخ را روی یک اتصال فراهم کرد. همچنین فشرده‌سازی هدرها با استفاده از `HPACK` معرفی شد. با این حال، چون HTTP/2 معمولاً روی TCP اجرا می‌شود، ازدست‌رفتن یک بسته می‌تواند باعث تأخیر در پردازش داده‌های جریان‌های دیگر شود.

**۵. HTTP/3**

این نسخه از پروتکل `QUIC` روی `UDP` استفاده می‌کند. قابلیت‌هایی مانند چندجریانی، کنترل ازدحام، انتقال مطمئن داده‌ها و رمزنگاری مبتنی بر `TLS 1.3` در QUIC فراهم شده‌اند. این طراحی اثر ازدست‌رفتن بسته‌ها بر جریان‌های مستقل را کاهش می‌دهد.

### چرا HTTP/3 از UDP استفاده می‌کند؟

UDP به‌تنهایی تحویل مطمئن و مرتب‌سازی داده‌ها را تضمین نمی‌کند، اما QUIC این قابلیت‌ها را در لایه‌ای بالاتر فراهم می‌کند. در HTTP/2، چند جریان روی یک اتصال TCP قرار دارند و ازدست‌رفتن یک بسته می‌تواند ارسال داده‌های همهٔ آن‌ها را موقتاً متوقف کند. در QUIC، جریان‌ها مستقل‌تر هستند و ازدست‌رفتن بسته در یک جریان لزوماً مانع پیشرفت جریان‌های دیگر نمی‌شود. همچنین QUIC می‌تواند زمان برقراری اتصال امن را کاهش دهد.

## سؤال دو: ارتباط‌های Stateless و Stateful

<div dir="rtl">

### الف) توضیح دسته‌بندی

در ارتباط `Stateless`، هر درخواست مستقل از درخواست‌های قبلی پردازش می‌شود و سرور برای تفسیر درخواست فعلی نیازی به نگهداری وضعیت درخواست‌های گذشته ندارد. در مقابل، در ارتباط `Stateful`، اطلاعات مربوط به تعامل‌های قبلی نگهداری می‌شود و پردازش درخواست فعلی می‌تواند به آن اطلاعات وابسته باشد. برای مثال، نگهداری اقلام سبد خرید کاربر در طول چند درخواست، نمونه‌ای از حفظ وضعیت است.

### ب) HTTP در کدام دسته قرار می‌گیرد و چگونه وضعیت مدیریت می‌شود؟

پروتکل `HTTP` ذاتاً `Stateless` است؛ یعنی هر درخواست باید به‌صورت مستقل قابل تفسیر باشد. برای ایجاد رفتار `Stateful` در برنامه‌های وب، می‌توان از `Cookie` و `Session` استفاده کرد. معمولاً سرور یک شناسهٔ نشست ایجاد می‌کند و آن را از طریق `Cookie` در اختیار مرورگر قرار می‌دهد. مرورگر این شناسه را در درخواست‌های بعدی ارسال می‌کند تا سرور بتواند اطلاعات نشست مربوط به کاربر را بازیابی کند. روش دیگری مانند استفاده از توکن‌های احراز هویت نیز وجود دارد. با این حال، استفاده از این روش‌ها ماهیت `Stateless` خود HTTP را تغییر نمی‌دهد.

</div>

## سؤال سه: ارتباط سرور به کلاینت، Webhook و Alerting

<div dir="rtl">

### الف) توضیح چالش

در مدل معمول `Client/Server` در HTTP، کلاینت آغازکنندهٔ ارتباط است و سرور معمولاً در پاسخ به درخواست کلاینت اطلاعات ارسال می‌کند. بنابراین، سرور نمی‌تواند بدون وجود یک درخواست یا کانال ارتباطی مناسب، در هر زمان پیام جدیدی را مستقیماً به کلاینت ارسال کند. این محدودیت در کاربردهایی مانند چت، اعلان‌های بلادرنگ و سیستم‌های هشداردهی چالش ایجاد می‌کند.

### ب) راهکارهای مقابله با این چالش

**۱. Polling**

در روش `Polling`، کلاینت در بازه‌های زمانی مشخص درخواست جدیدی به سرور ارسال می‌کند تا بررسی کند آیا اطلاعات جدیدی وجود دارد یا خیر. پیاده‌سازی این روش ساده است، اما ممکن است تعداد زیادی درخواست بدون تغییر اطلاعات ایجاد شود و اعلان‌ها نیز با تأخیر به دست کلاینت برسند.

**۲. Long Polling**

در روش `Long Polling`، کلاینت درخواست خود را ارسال می‌کند و سرور تا زمان آماده‌شدن اطلاعات جدید یا رسیدن به محدودیت زمانی، پاسخ را باز نگه می‌دارد. پس از دریافت پاسخ، کلاینت درخواست دیگری ارسال می‌کند. این روش می‌تواند تعداد درخواست‌های بی‌نتیجه را کاهش دهد، اما همچنان به درخواست‌های HTTP متوالی و مدیریت زمان انتظار نیاز دارد.

**۳. Server-Sent Events (SSE)**

در روش `SSE`، کلاینت یک اتصال HTTP ایجاد می‌کند و سرور می‌تواند از طریق همان اتصال، رویدادهای جدید را به‌صورت جریانی ارسال کند. این روش برای اعلان‌ها و به‌روزرسانی‌هایی مناسب است که عمدتاً از سمت سرور به کلاینت ارسال می‌شوند. ارتباط `SSE` یک‌طرفه است و برای ارسال داده از کلاینت به سرور باید از درخواست جداگانه‌ای استفاده شود.

**۴. WebSocket**

پروتکل `WebSocket` پس از برقراری اتصال، یک کانال ارتباطی دوطرفه ایجاد می‌کند. در نتیجه، کلاینت و سرور می‌توانند بدون ایجاد درخواست HTTP جدید برای هر پیام، داده ارسال کنند. این روش برای برنامه‌هایی مانند چت و ارتباطات بلادرنگ مناسب است، اما به مدیریت اتصال‌های پایدار نیاز دارد.

**۵. Webhook**

در روش `Webhook`، یک سرویس هنگام رخ‌دادن رویدادی مشخص، درخواستی HTTP، معمولاً با متد `POST`، به آدرسی از پیش تعیین‌شده در سرویس دیگر ارسال می‌کند. برای مثال، پس از تکمیل پرداخت، یک سامانه می‌تواند از طریق `Webhook` نتیجه را به سامانهٔ فروش اطلاع دهد. در این روش، سرویس دریافت‌کننده باید یک `Endpoint` قابل‌دسترسی داشته باشد و مواردی مانند احراز اصالت درخواست، تلاش مجدد در صورت خطا و جلوگیری از پردازش تکراری را مدیریت کند. `Webhook` بیشتر برای ارتباط بین سرویس‌ها استفاده می‌شود و به‌تنهایی راهکار عمومی ارسال پیام به مرورگر کاربران نیست.

در مجموع، انتخاب راهکار به نیاز برنامه بستگی دارد. `Polling` ساده است، `Long Polling` تعداد درخواست‌های بی‌نتیجه را کاهش می‌دهد، `SSE` برای ارسال یک‌طرفهٔ رویدادها مناسب است، `WebSocket` ارتباط دوطرفهٔ بلادرنگ فراهم می‌کند و `Webhook` برای اطلاع‌رسانی رویدادها بین سرویس‌ها کاربرد دارد.

</div>

## سؤال چهار: مشخص‌کردن اجزای URL

آدرس داده‌شده:

```text
ss://asghar:1234!!@ss.myproxy.com:1234#shadowSocks1
```

<div dir="rtl">

اجزای این آدرس به شرح زیر هستند:

| جزء | مقدار | توضیح |
|---|---|---|
| Scheme | `ss` | نوع طرح آدرس؛ در این مثال مربوط به Shadowsocks است. |
| Username | `asghar` | نام کاربری |
| Password | `1234!!` | گذرواژه |
| Host | `ss.myproxy.com` | نام میزبان سرور |
| Port | `1234` | شمارهٔ پورت |
| Fragment | `shadowSocks1` | شناسه یا برچسبی که پس از `#` قرار گرفته است. |

## سؤال پنج: انتخاب HTTP Status Code مناسب برای REST API

<div dir="rtl">

### سناریو ۱: پایگاه دادهٔ وب‌سایت دچار مشکل شده و درخواست‌های ورود انجام نمی‌شوند.

کد پیشنهادی: `503 Service Unavailable`

این کد زمانی مناسب است که سرویس به‌صورت موقت قادر به پاسخ‌گویی مناسب نباشد؛ برای مثال، به دلیل اختلال در پایگاه داده. اگر مشکل ناشی از یک خطای داخلی پیش‌بینی‌نشده باشد، کد `500 Internal Server Error` نیز می‌تواند مناسب باشد.

### سناریو ۲: نام کاربری واردشده در سایت وجود ندارد و ورود ناموفق است.

کد پیشنهادی: `401 Unauthorized`

این کد نشان می‌دهد که احراز هویت انجام نشده یا اطلاعات احراز هویت معتبر نیستند. برای جلوگیری از افشای اطلاعات حساب‌ها، بهتر است پیام خطا به‌صورت عمومی، مانند «نام کاربری یا گذرواژه نادرست است»، نمایش داده شود.

### سناریو ۳: وب‌سایت به دامنهٔ دیگری منتقل شده است.

کد پیشنهادی: `301 Moved Permanently`

این کد برای انتقال دائمی یک منبع به آدرس جدید استفاده می‌شود. اگر انتقال موقت باشد، می‌توان از `302 Found` یا `307 Temporary Redirect` استفاده کرد.

### سناریو ۴: تعداد درخواست‌های کاربر از نرخ مجاز بیشتر است.

کد پیشنهادی: `429 Too Many Requests`

این کد برای زمانی است که کاربر در یک بازهٔ زمانی، درخواست‌های بیش از حد مجاز ارسال کرده باشد. سرور می‌تواند در صورت نیاز از هدر `Retry-After` برای مشخص‌کردن زمان مناسب ارسال مجدد درخواست استفاده کند.

### سناریو ۵: تمدید JWT موفق بوده و توکن جدید در هدر پاسخ بازگردانده شده است.

کد پیشنهادی: `200 OK`

این کد نشان می‌دهد که عملیات تمدید توکن با موفقیت انجام شده است. توکن جدید می‌تواند در هدر پاسخ قرار بگیرد. اگر API هیچ محتوایی در پاسخ برنگرداند، `204 No Content` نیز ممکن است مناسب باشد؛ اما برای این سناریو `200 OK` انتخاب مناسبی است.

### سناریو ۶: کاربر از یک بازهٔ IP ممنوع شده و اجازهٔ دسترسی به سرویس را ندارد.

کد پیشنهادی: `403 Forbidden`

این کد نشان می‌دهد که سرور درخواست را دریافت و درک کرده، اما به دلیل محدودیت دسترسی آن را رد می‌کند. این وضعیت با خطای احراز هویت تفاوت دارد و برای محدودیت دسترسی ناشی از سیاست‌های سرویس مناسب است.

</div>

## سؤال شش: تعیین نوع پروکسی

<div dir="rtl">

### سناریو ۱: استفاده از سرورهای داخلی دانشگاه برای دریافت بسته‌ها به‌جای سرورهای مرکزی

نوع پروکسی: `Caching Proxy` یا `Repository Mirror`

در این روش، سرور داخلی دانشگاه بسته‌های موردنیاز را ذخیره می‌کند یا نسخه‌ای همگام‌شده از مخزن اصلی نگه می‌دارد. در نتیجه، کاربران می‌توانند بسته‌ها را از سروری نزدیک‌تر دریافت کنند و زمان دانلود و ترافیک شبکهٔ خارجی کاهش می‌یابد. برای نمونه، این روش برای مخازن بسته‌های `apt` در سیستم‌عامل Ubuntu کاربرد دارد. اگر سرور نسخه‌ای از مخزن اصلی را نگهداری کند، اصطلاح `Repository Mirror` دقیق‌تر است.

### سناریو ۲: تقسیم درخواست‌ها بر اساس مبدأ جغرافیایی آن‌ها

نوع راهکار: `Geo-aware Reverse Proxy` یا `Geo-aware Load Balancer`

در این روش، درخواست‌ها بر اساس موقعیت جغرافیایی کاربر یا نزدیک‌ترین منطقه به سرور مناسب هدایت می‌شوند. این کار می‌تواند تأخیر شبکه را کاهش دهد و توزیع بار بین سرورهای مناطق مختلف را بهبود ببخشد. البته این قابلیت ممکن است با روش‌هایی مانند `GeoDNS` نیز پیاده‌سازی شود و لزوماً همیشه به معنای استفاده از یک پروکسی مستقل نیست.

### سناریو ۳: اضافه‌کردن قابلیت احراز هویت به یک سرویس بسیار قدیمی

نوع پروکسی: `Reverse Proxy`

در این روش، یک پروکسی معکوس در جلوی سرویس قدیمی قرار می‌گیرد و درخواست‌ها را پیش از ارسال به سرویس اصلی بررسی می‌کند. پروکسی می‌تواند احراز هویت و کنترل دسترسی را انجام دهد و فقط درخواست‌های مجاز را به سرویس ارسال کند. به این ترتیب، می‌توان قابلیت احراز هویت را بدون تغییرات گسترده در کد سرویس قدیمی اضافه کرد.

</div>
